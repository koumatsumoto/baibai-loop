# 実装と文書の整理方針

次の作業者が投資判断に役立つシステムを理解・変更・運用できるよう、必要な意味へ短く辿れる形にする。量や網羅性を成果にせず、単なる短文化・別ファイルへの移動で済ませない。採否は[開発原則](doctrine.md#development-investment-policy)に従う。

## コードを正本にし、文書は入口を作る

規則・算式・field・分岐・既定値は所有コードを正本とし、referenceへ転記しない。まず型・名前・配置・関数を整理し、それで伝わらない意味・理由・必要な運用を残す。

- 同じ経済的意味・入力契約・変更理由は一ownerへ集め、callerはその入口を使う。汎用箱・薄い転送・設定層を共通化のためだけに増やさない。
- 一緒に変わる規則・型・補助処理・理由を近づけ、testのownerも明確にする。意味・更新周期・失敗条件・依存が異なる処理は、見た目が似ても分ける。
- コメントは局所的な理由だけ。逐語説明、進捗、Issue転載を置かない。文書は目的・構造・責務・入口を案内し、全file/functionの第二仕様書にしない。

通常変更でも周囲のcode/test/文書を一緒に読み、重複・旧記述を整理する。重要な経済的意味・操作順・復旧条件は「コードにある」だけで削らない。

## 何をどこに残すか

| owner | 残すもの |
| --- | --- |
| README・glossary | 製品の入口・最小導線／採用名称と意味の区別。 |
| doctrine・architecture | 価値・戦略・採否／責務・依存・正本と理由。未実装の目標を現状にしない。 |
| skill・運用手順 | 開始・操作・完了/再開と注意。CLI helpの全転記はしない。 |
| 実装・test付近 | 局所的な設計理由・非自明な規約。 |
| Issue・固定Git履歴 | 企画・比較・採否・実験・過去の進捗。未採用案は現行仕様と分ける。 |

referenceは他のownerだけでは伝わらない領域間の意味・利用制約に限る。役割を失えば統合/削除する。

## 追加・変更・統合時の判断

誰のどの判断に必要か、正本はどこかを先に決める。参照で足りる説明を複写せず、旧仕様・重複・進捗・未採用案を整理する。実装との不一致は製品価値からどちらを直すか判断し、文書だけ追随させない。

自己reviewでは、重要な判断理由の残存先、owner・名前・配置、リンク/操作入口/生成物の整合を確認する。通常PRへ無関係な全面検査や恒久チェック台帳を追加しない。例として価格注記の閾値は実装へ寄せるが、注記は買付判断でないことや未知日を陰性にしない理由は残す。

## 全体見直しを行う場合

明示された全体監査は通常PRと分け、次を行う。

1. 目的・構造・領域の意味・運用を現行実装と照合し、基準を整理する。
2. 基準commitの全追跡fileをIssueへ列挙し、一件ずつ本文・責務・caller・test・説明を読む。変更不要の理由と、途中の追加/削除/移動/再変更も追跡する。
3. L1→L2→L3→人間報告→台帳→表示を横断し、identity・時点・単位・欠測・再開・部分失敗・公開と依存を検証する。
4. 最終HEADで影響箇所と横断経路、CIと必要な実データ受入を再確認する。未読/未解決を完了にせず、PR/test数だけで品質を認定しない。

本文読取・設計適合・test・実データ受入は別に記録する。チェックリストは第二仕様書にせず、改名/削除で確認対象を消さない。文書削減は原本・判断・取引履歴の削除許可ではない。
