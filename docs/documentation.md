# 実装と文書の整理方針

文書の目的は、投資判断と資本配分に役立つシステムを、次の作業者が誤解なく理解・変更・運用できること。追加量や網羅した説明数ではなく、必要な情報へ短く辿れるかで評価する。削減は情報の価値と責務を判断して行い、単なる短文化や別ファイルへの移動で済ませない。

## コードを正本にし、文書は入口を作る

実装の規則・算式・field・分岐・既定値は、所有するコードを読めば分かる状態にする。同じ内容をreferenceやREADMEへ転記して二つの正本を作らない。まず実装と配置を整理し、それでもコードだけでは伝わらない意味・理由・運用を文書へ残す。

- **同じ責務は一か所へ集める。** 同じ経済的意味・入力契約・変更理由を持つ処理は所有者を一つにし、callerはその入口を使う。共通化のためだけの汎用箱、薄い転送module、設定層を増やさない。
- **一緒に変わるものを近くへ置く。** 規則、型、局所的な補助処理、コメントを責務の近くへ配置する。testも検証するownerとの対応が分かる構成にし、別領域のfixtureや内部実装へ不必要に依存させない。
- **見た目だけで共通化しない。** 似たコードでも意味・更新周期・失敗条件・依存方向が異なるなら分ける。共有すると分岐や引数が増え、独立した変更を難しくする場合は、局所的な重複を許す。
- **コメントには理由を残す。** なぜその方法・境界を選んだか、何と混同してはいけないかを所有実装の近くへ簡潔に書く。コードの逐語説明、過去の進捗、Issue本文の転載は書かない。型・名前・関数分割で明らかにできることは先にコードを直す。
- **文書は抽象化した案内にする。** 製品の目的、全体構造、責務の境界、索引、読み始める入口を案内する。全ファイル・全関数の説明一覧や、実装詳細の第二仕様書は作らない。重要な経済的意味や運用の順序・復旧条件は、コードに存在するという理由だけで削らない。

この方針は今回限りの清掃ではなく、通常の変更にも適用する。追加箇所だけを継ぎ足さず、変更する責務の既存コード・test・説明を一緒に読み、重複と古い記述をその変更内で整理する。

## 何をどこに残すか

- README：製品の入口と、目的に応じた最小の導線。
- glossary：採用する日本語名・英語名と意味の区別。実装配置や操作手順は複写しない。
- doctrine：ビジネス価値、背景、投資戦略、リスク受容、開発の採否基準。
- architecture：システム全体の構造、責務・依存・正本の境界、その分け方の理由。現状と未実装の目標を区別する。
- skills・運用手順：実際の開始・操作・完了/再開に必要な手順と注意。CLI helpや実装の全転記にはしない。
- 実装・testの近く：局所的な設計理由、非自明な規約、誤って変更すると意味を壊す制約。コードから明らかな処理内容の言い換えは不要。
- Issue・固定Git履歴：企画、比較、採否の経緯、有限の実験結果、過去の進捗。未採用案を現行仕様へ混ぜない。

referenceなどの中間文書は、上記だけでは伝わらない重要な領域間の意味や利用制約に限る。既にある文書の存在を前提にせず、役割がなくなれば統合・削除する。

## 追加・変更・統合時の判断

1. 誰のどの判断・作業に必要かを先に確認する。実装を読めば分かるfield、分岐、算式、ファイル紹介は文書へ重ねない。
2. 同じ意味の正本を一つにする。参照で足りる説明は複写せず、局所的な理由を全体文書へ持ち上げない。
3. 残す理由がない旧仕様、重複、古い進捗、未採用の将来案を削る。重要な背景・経済的意味・責務の境界まで、実装にあるという理由で落とさない。
4. 統合先を読めば元の重要な判断理由に辿れるか、リンク・操作入口・生成物との矛盾がないかを横断確認する。削減のために新しい説明層を作らない。
5. 文書と実装が食い違う場合、実装に合わせて言い換えるだけで済ませず、製品価値・戦略からどちらを修正すべきか決める。
6. PRの自己レビューでは、規則の正本が一つか、配置と名前からownerへ辿れるか、コメントが理由を説明しているか、入口文書とリンクが現状を指すかを確認する。変更しない領域の全面再検証や、恒久的なチェック台帳の追加を通常PRへ要求しない。

例：価格注記の閾値や三値判定の分岐は所有実装を見る。「注記は買付判断ではない」「未知の日を陰性とみなさない理由」は必要な意味である。全体の責務はarchitecture、局所的な算術規約の理由は該当実装の近くに置く。

## 全体見直しを行う場合

全体監査を明示的に依頼された場合は、通常PRの範囲確認と区別し、次の順で完了を判断する。

1. **基準を整える。** 目的・architecture・領域の意味・運用を現行実装と照合し、古い仕様や継ぎ足しを整理して自己レビューする。未実装の企画を現行構造として書かない。
2. **全件を追跡する。** 基準commitの全追跡ファイルをIssueのチェックリストへ列挙し、一件ずつ実読する。責務・配置・重複・呼出し元・test・説明を確認し、変更不要の判断にも理由を残す。途中の追加・削除・移動・再変更も追跡する。
3. **横断して検証する。** 個別の確認後に、L1の受領からL2・L3・人間の報告・台帳・表示までを通して読む。identity、時点、単位、欠測、再開、部分失敗、公開の境界と、依存方向・共通化・入口の一貫性を確かめる。
4. **最終状態を再確認する。** 修正後のHEADで影響箇所と関連する横断経路を再レビューし、CIと必要な実データ受入を照合する。未読や未解決を完了にせず、PRの数・CI成功・チェック数だけで全体品質を認定しない。

確認記録は、本文読取・設計適合・テスト実行・実データ受入を区別する。チェックリストを製品仕様の第二正本にせず、削除・改名でも確認対象が消えた扱いにしない。説明の削除は、必要な原本・判断・取引履歴の削除を許可するものではない。
