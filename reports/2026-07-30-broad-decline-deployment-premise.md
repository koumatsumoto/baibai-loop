# 広範下落局面での資本展開 — 前提の計測（#668）

価値tier: T1 — 「安いときに多く買う」を事前規律にできるかを、リポジトリ自身の計器で先に確かめる。

#668 は「バーゲンが最も広く供給される広範下落局面で、1 回あたりの金額目安と恐怖局面の不作為が投入を細らせる」という観察から、機械 fact で判定する stage 表を governance へ事前登録する提案である。stage の閾値と金額は issue で「未決事項（人間の判断）」とされている。

**その数値を決める前に、提案が乗っている 2 つの前提を測った。どちらも支持されなかった。** この report は測定結果と、それが資本展開の設計に何を意味するかを記録する。

## 0. 判定

```yaml
premise_bargain_supply_widens_in_decline: not_supported
premise_per_order_guide_is_the_binding_constraint: no_operational_record
protocol_as_specified: not_adopted
```

## 1. 再現手順

```bash
uv run baibai-engine screening market-snapshot --asof 2026-07-29 --weeks 250
uv run baibai-engine position ledger
```

観測日 2026-07-30。市場側は週次点 250 件（2021-10-20〜2026-07-29、60 営業日リターンが解決するのは 248 件）、benchmark は `1321`。候補供給側は `data/screening/calibration/panel-*.csv` の 46 か月分（2022-09-30〜2026-06-30）で、`rules_hash` は 46 本すべて `f4f3cfffe012f4d9` — rules 変更で汚染されていない時系列である。分位点は `statistics.quantiles(..., method="exclusive")` による。

## 3. 前提 (i): 広範な下落はバーゲンを広く供給するか — 支持されない

46 か月の point-in-time panel を、同じ asof の市場状態と join した。これは edge の主張ではなく純粋な記述命題なので、リポジトリの既存計器で直接測れる。

| 市場状態 | n | 通過候補数（中央） | 通過候補 E[r] 中央 | 上位 20 平均 | 上位 5 平均 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 60d ≤ −5% | 4 | 396 | 1.79% | 8.55% | 10.11% |
| −5% < 60d ≤ +5% | 20 | 413 | 1.70% | 8.22% | 9.91% |
| 60d > +5% | 22 | 381 | 1.43% | 8.10% | 9.79% |

```
corr(60d return, 通過候補数)        = +0.026
corr(60d return, 通過率)            = -0.151
corr(60d return, 通過候補 E[r] 中央) = -0.212
corr(60d return, 上位 20 平均 E[r])  = -0.017
corr(60d return, 上位 5 平均 E[r])   = -0.078
```

読み取れること。

- **候補の絶対数は下落局面で増えない。** 中央値は 396 / 413 / 381 で、相関は +0.026。「最も広く供給される」を支える証拠がない。これは小標本の揺らぎではなく、ほぼ平坦な線である。
- **実際に買われる上位の質はほとんど動かない。** 上位 5 平均 E[r] は 10.11%（下落）対 9.79%（上昇）で、市場サイクル全体を通じた差は **0.32 ポイント**。相関 −0.078 は 0 と区別できない。プールの中央値（1.79% 対 1.43%、相関 −0.212）が最も強い信号で、それでも弱い。
- 通過**率**がわずかに上がるのは母集団が縮むためで、候補が増えているのではない。

つまり「下落局面では買うべきものが増えるので、1 回あたりを増やしたい」は、後半（増やしたい）の根拠として前半（増える）が使えない。**候補は増えないのだから、投入を増やす唯一の経路は 1 銘柄あたりの金額を増やすことになる。** それが何を意味するかは §5 で見る。

限定: 月末サンプリングなので月中の底を外す。下落バケットは n=4。窓は重なる。ただし候補数の平坦さはこれらの限定では説明できない。

## 4. 前提 (ii): 1 回あたりの金額目安が律速か — 運用記録が無い

`proposal` テーブルは **0 行**で、`budget_guide_exceeded` / `budget_guide_under` が本番で発火した記録は 1 件も無い。canonical ledger の非 migration 実発注は 1 件（3836、¥1,204 × 200 = ¥240,800）で、目安 20〜30 万円の内側にある。migration で取り込んだ既存保有には ¥355,700（9715）があり、目安超過の建玉は protocol 無しで既に成立している。

「目安が律速になっている」を示す観測は現時点で存在しない。同じ governance の別の制約 — proposal と reservation を投資価値 rank 順に 1 件ずつ進める直列規律、および全 kind を通じて active session 最大 1 件 — のほうが、下落局面で投入本数を決めている可能性が高い。protocol はこの 2 つを「緩めないもの」に据え置いていた。

## 5. 機構: 金額目安は上限ではなく充填目標である

`research/opportunity.py` は提案数量を `max(floor(budget_max_yen / lot_notional), 1) * BOARD_LOT` で決め、`proposals/store.py` は approve 時に同じ式で再計算して厳格一致を要求する。1 単元が上限を超える場合は 1 単元 + `budget_guide_exceeded` warning で、**発注は止まらない**。

帰結が 2 つある。

1. **20〜30 万円は cap ではない。** Capital guidance が「hard cap ではない」と書いているとおりで、stage 表がこれを「1 回あたりの上限」列に置いたのは既存 policy の無断の厳格化だった。
2. **上限側の数値を上げると、機械提案の数量がそのぶん増える。** ¥600,000 を渡せば機械はその枠を埋める lot 数を提案する。「上限まで使う義務はない」を実現する唯一の方法は「その金額を渡さない」＝ stage を使わないことなので、この免責は運用上ほぼ無内容になる。

§3 と合わせると、stage の効果は「増えた候補に広く配る」ではなく「増えていない候補の 1 銘柄へ厚く張る」である。protocol が守ろうとした分散の直感と、機構が実際にする動作が逆を向いている。

## 6. 集中上限との算術

canonical ledger の実測（`position ledger`、2026-07-15 基準）:

```yaml
book_capital_yen: 4871100
total_capital_yen: 5006100
```

`max_ticker_concentration_pct = 10.0` の警告線は ¥500,610。stage 2 の ¥600,000 は新規銘柄でも **11.99%** となり、必ず ticker 集中 warning を踏む。「position policy の cap は緩めない」と ¥600,000 は、資本が ¥6,000,000 を超えるまで同時に成立しない。

cap は warning であって禁止ではないという反論は成り立つが、そうすると protocol は「条文上 cap を緩めないまま、cap 超過発注を常態化させる事前コミットメント」になる。価値階層の「T1 の改善であっても T2 の必須関門を弱める案は採用しない」は、関門の条文ではなく関門の実効性を守る規定である。

## 7. 閾値そのものが再現しない

`market-snapshot` の週次点は asof から 7 日刻みの格子で、`--asof` を省くと「その日の最新営業日」がアンカーになる。同じ 250 点・同じ閾値で、アンカーの曜日だけを変えた結果:

| アンカー | stage 1 該当週 | 比率 |
| --- | ---: | ---: |
| 2026-07-29 | 11 | 4.4% |
| 2026-07-28 | 12 | 4.8% |
| 2026-07-27 | 11 | 4.4% |
| 2026-07-24 | **6** | **2.4%** |
| 2026-07-23 | 9 | 3.6% |
| 2026-07-22 | 11 | 4.4% |
| 2026-07-21 | 12 | 4.8% |

stage 1 の該当頻度は 6〜12 週（2.4〜4.8%）の間でアンカー次第に動く。「年 1 回程度」という頻度設計は観測日の曜日で 2 倍変わる。stage 2 は 4 週で安定していた。

さらに人間は任意の日に判断するので実運用の評価頻度は日次であり、週次格子で数えた頻度は運用の頻度ではない。週次格子は 2024-08-05（この窓で最大の下落日）を stage 2 から取りこぼしている。

## 8. 条件セットが速い下げに反応せず、回復後に反応し続ける

**入口が遅い。** 観測日 2026-07-29 の市場状態:

```yaml
benchmark_return_20d: -0.1337   # 250 週中 2 番目に深い（最深は 2024-08-07 の -15.56%）
benchmark_return_60d: +0.0273
breadth_pct_above_ma20: 0.567
regime: risk_off_selloff
```

20 営業日で −13.4%、`regime` も `risk_off_selloff` でありながら、60d 条件だけを見る stage 表では「通常」判定になる。breadth 56.7% なので「広範ではない」と読むことはできるが、その判断は表からは読めない。

**出口も遅い。** 60 営業日リターンは trailing 窓なので、底を打って全面回復したあとも数週間 −8% を割ったままになる。stage 1 該当週の breadth を見ると:

| 週 | 60d | breadth |
| --- | ---: | ---: |
| 2022-03-16 | −9.32% | 51.7% |
| 2024-10-02 | −8.20% | 49.0% |
| 2025-04-23 | −11.94% | 71.9% |
| 2025-04-30 | −8.04% | **88.7%** |

2025-04-30 は上場銘柄の 88.7% が 20 日移動平均を上回っている — 「広範な下落」の真逆 — にもかかわらず、stage 1 が成立して 1 回あたりの金額が倍になる。protocol が防ごうとした失敗（恐怖局面の不作為）ではなく、その裏側の失敗（反発後に大きく買う）を制度化する経路である。

## 9. 計測経路が名目だった

宣言されていた計測経路は「ledger の execution / **contribution** × market-snapshot 履歴の機械 join」だが、`ledger_event` の実データは `execution` 10 / `opening_balance` 1 / `reservation` 12 で、**`contribution` は 1 件も記録されたことがない**。stage 2 の主効果である追加入金は、存在しない event type の上に計測経路を宣言していた。

execution 側も全件 2026-05-07〜2026-07-15 で、この期間に stage 週は 1 つも無い。しかもこの join が測るのは protocol の**遵守**であって**効果**ではない。柱 5 の「計測手段を持たない機械的機能は追加しない」は、効果を反証できる計測を要求している。

## 10. 結論

**stage 表を governance へ入れない。** 前提 (i) は測って支持されず、前提 (ii) には運用記録が無く、動かそうとした数値は cap ではなく充填目標で、その金額は集中上限を超え、閾値は観測日の曜日で 2 倍動き、宣言した計測経路の片側にはデータが 1 件も無い。§5〜§9 は文言の修正では消えない — それぞれが設計の一部である。

この report から governance へ持ち込むのは 1 点だけで、それは #668 と独立に真である: **金額目安の上限側は機械にとって充填目標であり、上げた分だけ 1 銘柄への提案数量が増える。** Capital guidance がこれを書いていなかったので、同節の数値がどう効くかが読めなかった。

残る問いは #668 のもとの動機に属する。「恐怖局面の不作為をどう防ぐか」は依然として実在する課題だが、計測が示したのは、その答えが 1 回あたりの金額ではないということである。候補数が増えない以上、下落局面で投入を増やす経路は 1 銘柄への集中しかなく、それは集中上限が先に止める。投入本数を決めているのが直列規律（proposal / reservation を 1 件ずつ、active session 最大 1 件）である可能性は §4 で見たとおりだが、これも現時点では観測ではなく仮説である。**`proposal` が 0 行である間は、どちらの律速仮説も検証できない。** 先に必要なのは protocol ではなく、投入経路の運用記録である。

## 11. 監視事項

- `proposal` テーブルに行が入り始めたら、`budget_guide_exceeded` / `budget_guide_under` の発火と、rank 順の直列進行で 1 サイクルに何件まで到達したかを数える。どちらが律速かはそこで初めて答えが出る。
- calibration panel が増えるたびに §3 を再計算する。下落バケットは現在 n=4 で、深い局面が 1 つ増えるだけで結論が動きうる標本である。
- `breadth_pct_above_ma20` が比率で出る点は、閾値を書く側が 100 倍間違えうる面として残っている。
