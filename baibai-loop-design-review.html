1. 30 秒サマリー：2 つのループ

Baibai-Loop の目的はただ一つ、「お買い得な日本株を機械的に拾い、トレード成績を最大化する」ことです。そのために、性質の違う 2 つのループを意図的に分離して回します。

  • 運用ループ（取引プロセス）：検証済みの screening system を適用し、具体的な売買判断（どの銘柄を・いくらで・何株）に落とす。screening 論理そのものは触らない。カデンスは機会ごと・週次。
  • 改善ループ（改善プロセス）：その screening system が機能しているかを、母数が極小の個人売買結果ではなく全候補の forward-only backtest（大 N）で検証し、keep/kill/review を判定して rules / playbooks / config を改訂する。カデンスは日次・週次。

2 つのループの接合点は 「検証済みの screening system（rules / playbooks / config）」ただ 1 点です。改善ループがそれを更新し、運用ループが現行版を消費します。データ源・成果物・管理面はすべて別です。

2. アーキテクチャ

2.1 3 層インフラ（L1 / L2 / L3）

2 つのループは、事実・分析・判断を物理的に分ける 3 層インフラの上で動きます。層の所属は置き場所ではなく成果物の性質で決まり、判定基準はただ一つ「人間の判断が入るか」です。

層実体性質
L1 データ層 data/screening/market.sqlite（J-Quants 価格・財務 / EDINET metrics / JPX 規制） 全上場銘柄の再現可能な事実。coverage は fail-fast で検証する
L2 分析層 screen lanes・selection lenses・軸別スコア・forward 計測（replay / lane-cohorts / ablation / scorecard）。機械ふるいの事実出力 = records/04-candidates/ 決定論的・閾値固定の機械処理。すべて forward 計測に接続する
L3 判断層 records/（macro context / research / trades）＋ reports/ 人間 + AI 下書きの解釈と判断。screening 効果の検証は全候補 backtest（改善ループ・大 N）が担い、trades は Q2 執行品質の信号を供給する

AI / スクリプトが依存してよい安定契約は 2 面だけ

CLI の YAML 出力と SQLite schema の 2 つに固定されています。判断と帰責は人間（L3）に残し、AI は L1 / L2 の事実に grounded な下書きを作る、という役割分担です。汎用 feature store / BI / MCP / API server などのサービング層は導入しません。

2.4 現状の実装構造（src の実体と結合）

理想モデル（3 層 + 2 ループ）に対し、実際の src/baibai_loop/ はサブシステム境界で割れておらず、ロジックがフラットに同居しています。レビューの土台として、現状の実体を正直に置きます。

パッケージ / モジュール行数ファイル担う責務

validate/3,27219candidates / research / trade / ledger / macro / policy の schema・業務ルール検証
ledger/3,147152 責務が同居：① 計測系（forward telemetry / scorecard）② tracking 系（decision register / trades）
stats/1,1286macro 統計 series 取得。他に依存されない独立パッケージ
macro_context.py1521マクロ環境分析の手動補助。薄い top-level モジュール（機械化されていない L3）

理想モデルと実装のギャップ（= レビュー対象）

  • サブシステム未分離：理想は「マクロ分析 / 銘柄スクリーニング / トレード」の 3 サブシステムだが、実体は screening/ に大半が集中し、ledger/ が計測と tracking を兼ねる。folder がドメイン境界を表現していない。
  • パッケージ循環：screening → ledger の逆 import が 1 本あり、依存が一方向に整理できていない。
  • macro が薄い手動層：macro_context.py は 152 行で、L1 統計 → L2 機械指標への落とし込みが無く、判断（L3）に直結している。

これらは §6 レビューの論点で扱います（既存の open issue #257 マクロ機械化・#258 フォルダ再編が対応候補）。

3. 取引プロセス（運用ループ）

3.1 全体フローと段階的規律

運用ループの本質は 段階的に厳しくなる規律で機械が裁量を縛りながら、銘柄を 1 本ずつ通すことです。母集団（全上場普通株）から始まり、liquidity 絞り込み → lens → kill switch → regime ゲート → 集中度ゲート と狭めて、最後に「いくらで何株」の売買提案を人間判断に上げます。

3.2 機械スクリーニング（4 lane の OR）

run は SQLite だけを読み（cache_only、provider API に触れない）、全上場普通株を母集団に 4 つの playbook-linked lane を OR で評価します。各 lane は slug だけでは意味が掴みにくいため、① 正式英語名 ② 漢字要約名をセットで併記します。

slug① 正式英語名② 漢字要約名一言で
valuation-reversionValuation Mean-Reversion株価評価の平均回帰（割安修正）業種比・自己レンジ比で割安化した倍率が平均へ戻るのを狙う
cash-rich-asset-discountCash-Rich Asset Discount現金潤沢・資産割安潤沢な現金・純資産に対し時価総額が小さい銘柄を拾う
cashflow-yield-discountCash-Flow Yield Discount現金創出力の割安営業 CF 利回り（CFO / 時価総額）が高い割安
sales-discount-growthSales-Multiple (P/S) Discount with Growth増収・売上割安P/S 業種比割安 × 売上成長が残る調整銘柄

設計判断：事実層と分析層を分ける

時価総額・売買代金・上場期間・JPX 規制 flag はスクリーニング段階では除外せず candidates に記録するだけです。research 推奨への絞り込み（時価総額 100 億円以上・20 日平均売買代金 1 億円以上・上場 182 日以上・規制除外）は後続 select（selection.liquidity）で初めて効きます。candidates は事実層なので「なぜ割安か」「採用すべきか」は一切書きません。

3.3 リサーチ候補選定（select + regime lens）

select は通過銘柄リストとマクロ環境分析を組み合わせ、リサーチ着手候補を絞る triage 層の機械処理です。lens は候補を「除外」せず「順位付け」に使います（gate ではない）。

lens目的扱い
fast_dislocation
短期急落・売られすぎ		一時的に売られすぎた候補を上位化価格下落 trigger ＋ fundamental guard を 2 件以上・2 系統以上要求
long_hold_survivability
長期保有耐性		短期 thesis が外れた時の保有耐性を可視化high/medium/low/unknown の annotation。ranking に使わない
prior_research
既往調査による抑制		deferred / rejected の再登場を抑制ledger の revisit_after / expires_at を尊重

market regime lens は SQLite の日次足から benchmark proxy 1321（日経225 ETF）の 20/60 営業日リターンで相場局面を分類します（固定閾値・grid search なし）。risk_on_rally（20 日 ≥ +3%）のときだけ fast_dislocation の ranking boost を中立化します（指数モメンタムが強い局面で anti-momentum な急落銘柄が構造的に劣後するため）。

3.4 リサーチ → 売買提案 → 人間判断 → 執行

research（investment memo）は candidates の事実と macro context を統合する分析層です。単一総合点に畳まず、4 軸（Valuation / Mean-Reversion / Catalyst / Positioning-Liquidity）に strong/weak/neutral の寄与だけ付けます。全 packet で反対仮説（構造的な下落理由）を必ず書き、割安が「罠」でないことを能動的に反証します。

  • kill switch（entry 不可）：決算またぎ・日銀会合前日・FOMC 前日・stale/future macro での無条件 proceed。
  • entry preflight の regime ゲート：risk_on_rally / unknown での proceed は hard-block（→ starter へ格下げ）。validator が強制する。
  • 集中度ゲート：(a) research preflight で sector_33 / playbook が 50% 超は proceed の hard trigger、(b) trade validator で sector 45% / playbook 35% / ticker 8% 超を error として gate。
  • 売買提案（GitHub Issue）：research の採用結論を「どの銘柄を・いくらで・何株」の具体提案にし、人間が承認 / 修正 / 却下する。提案・承認の場は Issue、その決定の機械正規化は records/_ledger/。
  • 売買執行記録（trades）：承認済み判断の注文・約定・保有・決済を記録（orders[] と executions[] を分離）。約定結果は改善ループへ Q2 信号として還流する。

「売買提案」は #252 で運用ループに明示化されたステージ

従来は research の結論から trades へ直結していましたが、「research の thesis（個別の採否）」と「portfolio 視点の具体提案（いくらで何株・集中度・timing）」は別判断です。後者を 売買提案 GitHub Issue として独立させ、人間判断の入口を明示しています（records にディレクトリは持たず、結果は ledger と trades に落ちる）。

4. 改善プロセス（改善ループ）

4.1 なぜ backtest 駆動か（Q1 / Q2 / Q3 と母数）

改善ループの設計の肝は、性質の違う 3 つの問いを直交する別問いとして分け、それぞれ母数の合う計器で測ることです。screening 論理の質を測れる大 N の計器は backtest ただ 1 つで、個人の実トレードは母数が極小すぎて screening の優劣を統計検証できません。

問い検証対象データ源 / N計器
Q1 論理の質lane / lens / regime が forward alpha を生むか全候補母集団の過去 replay ／ 大 Nbacktest（lane-cohorts / replay / ablation / scorecard）
＝改善ループの主軸
Q2 執行の質sizing / timing / exit / kill-switch を正しく運用したか自分の実トレード ／ 極小 Ntrade review ＋ counterfactual
（改善ループへ Q2 信号として）
Q3 個別 thesisこの銘柄の回帰が想定通りか個別トレード ／ n=1事例学習（統計ではない・仮説源）

バックテストの線引き（よくある誤解）

これは「バックテストしない」基盤ではありません。screening（lane / lens / regime / 閾値）の効果は、過去週を look-ahead を排して replay する multi-axis backtest で積極的に検証し、その計測で lane や閾値を改訂します。避けるのは ①未来データへの閾値 grid search・最適化（data snooping 回避） ②累積リターン / Sharpe / MaxDD の track-record claim ③trade 単位の累積 backtest ── の 3 つだけです。

4.2 forward 計測 6 本と scorecard の keep/kill/review

baibai-loop-ledger は 6 本の forward 計測コマンドを持ちます。いずれも勝敗の件数集計ではなく、outcome を playbook / evidence / macro / sizing / execution に帰属させる feedback です。#254 で追加された lane-scorecard / proposal-scorecard が、生の計測を keep/kill/review の「判定」に変換する層です。

CLI計測対象役割
benchmark実保有 positions の絶対・相対リターンと attribution実トレードの事後検証
screening-replayrecommended queue（top N）の asof+1w/4w forward return（1321 比）profile 採否を 6〜8 週で判断、直近は hold-out
lane-cohorts週次 candidates の全銘柄を lane 別 cohort で集計どの割安タイプが効いたか（生計測）
selection-ablationranking 構成要素・lane を 1 つずつ無効化した variant の Δfull機能の削減・維持判断
lane-scorecard #254lane-cohorts を週跨ぎで pool し、pooled mean ＋ bootstrap 95% CI を baseline と比較lane の keep / kill / review を判定
proposal-scorecard #254recommended queue（実取引提案単位）を pool し baseline と比較proposal レベルの relevance overlay（小 N・directional）

lane-scorecard の判定ロジック（cut point 固定・bootstrap seed 固定・grid search なし）：

判定条件意味
keeplane の 95% CI が baseline（全候補平均）より上選定価値あり。lane を維持・強化
kill_candidateCI が baseline より下平均以下の選定。lane 削除候補
reviewCI が baseline を跨ぐ、または n < min_resolved（母数不足）directional のみ。判断保留
baselineall_candidates 行比較の固定参照

C0-gate の実測（2026-06-21、6 asof）

scorecard は backtest-runbook §6 の既知結果を独立再現しました：cash-rich-asset-discount が baseline 比 +2.10pt で keep（全 lane 中最強・config の lane 順先頭と整合）、cashflow-yield-discount +1.14pt で keep、sales-discount-growth / valuation-reversion は CI が baseline を跨ぎ review。感度頑健（min_resolved・bootstrap 反復・horizon 単調）。計測記録は reports/2026-06-21-lane-scorecard-c0-methodology.md。

4.3 計測 → backlog → 改訂 PR のサイクル

改善は GitHub Issue の改善バックログで管理し、screening rules / playbooks / config の改訂（PR）に落とします。reports/ はその計測の dated ダイジェスト（数値を読んで「次に何を直すか」を残す L3 解釈）。

貫く原則：計測経路のない機能は足さない

config の lane 順や sector 分散上限は、コメントに計測根拠が紐づきます（例：lane 順が cash-rich 先頭なのは lane-cohorts と selection-ablation の Δfull が最大だから）。追加する各指標は forward 計測経路を 1 行で説明でき、駆動する最初の具体決定を名指せること——名指せない指標は足しません。lane-scorecard はこの原則を判定として明文化したものです。

6. レビューの論点（壁打ちの叩き台）

現状設計を踏まえ、次に議論すべき構造的論点を置きます。いずれも「機能追加」より「計測で示しながら整理・分離する」方向の検討です。

#論点現状検討の方向対応候補
A マクロ分析が手動・薄い macro_context.py 152 行。L1 統計 → L2 機械指標の落とし込みが無く、L3 判断に直結 政策金利 / 国債 / 原油 / イベント等を L2 の最小機械指標に。各指標が「どの判断を駆動するか」を 1 行で言えるものだけ。N≈1 の honest な扱い open issue #257

一言でまとめると

Baibai-Loop は 2 つのループです。取引プロセス（運用ループ）は事実（L1/L2）を決定論的に作り、段階的に厳しくなる規律で機械が裁量を縛りながら銘柄を 1 本ずつ通し、「いくらで何株」の売買提案を人間判断に上げます。改善プロセス（改善ループ）は、screening が機能しているかを——母数が極小の個人売買結果ではなく——全候補の forward-only backtest（大 N）で検証し、#254 の lane-scorecard が keep/kill/review を判定して改善 Issue → 改訂 PR に繋ぎます。残る構造的論点は ①マクロの機械化（#257） ②サブシステム分離（#258）で、いずれも「計測で示しながら整理する」方向です。
