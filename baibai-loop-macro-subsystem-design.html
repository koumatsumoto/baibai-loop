この版の方針（簡略化）

マクロ分析を無理にループ化すると過剰に複雑になる。改善はやりながら都度でよいので、formal な loop / retro / 成長判定機構は作らない。macro は「ループ」ではなく capability（データ取得層 ＋ リサーチ実践）として持つ。データ取得層は Provider モジュール設計で各ソースの実装を整理する。狙いの大本は「マクロ環境分析の能力を育て、トレード判断に効く環境読みを供給する」こと。

1. 位置づけ：macro は capability（ループにしない）

マクロ分析は独立した capability（サブシステム）として持ちますが、formal なループにはしません。retro / calibration / ratchet のような成長判定の機構は置かず、調査方法やナレッジは使いながら都度洗練します。ループとして回るのは従来どおり運用ループと改善ループの 2 つで、macro はその起点に環境読みを供給する capabilityです。

2. 目的とスコープ境界（広い問い × lever 規律）

capability の価値は「環境を読んでトレード判断を駆動する」こと。問いは広く許し、規律で接地します。

スコープ境界：問いは広く、規律は狭く

対象は macro / 市場の全域（世界経済・政策・金利・FX・商品・主要 INDEX・crypto / risk-sentiment・セクター・地政学）。ただし 各分析は必ず「トレード上の lever」を名指す——どの sector を厚 / 薄、gross / cash、theme exposure、entry timing / kill のどれを動かすか。lever を名指せない問いは repo の対象外（汎用リサーチ助手化の歯止め）。

  • 「Strategy 社財務 × BTC 長期展望」→「crypto 隣接 JP 銘柄 / risk appetite」に route するなら in
  • 「直近イベントを踏まえた世界経済の長期変化」→「risk posture ＋ sector tilt」に route、in

3. サブシステムの中身（3 種：データ / 分析成果 / ナレッジ）

capability が抱えるのは性質の違う 3 種類。機構ではなく「置き場所の整理」として捉えます。③ ナレッジは使いながら都度たまるもので、formal な計測はしません。

種正体性質
① データ統計 series（provider 取得・再現可能・provenance 付き）事実
② 分析成果dated・sourced な環境リサーチ（scenario / risk / forward view ＋ lever）判断・成果
③ ナレッジ調査方法のコツ・データソース確認手順・lessons（都度たまる。playbook 化は必要になってから）メタ知識

4. データ取得層：Provider モジュール設計

データ取得層は Provider パターンで組みます。各データソースを共通 interface を実装する独立モジュールに隔離し、認証・rate limit・パースなどソース固有の事情をその module 内に閉じ込めます。新ソース追加 = provider モジュールを 1 つ足して series を登録するだけ、に整理します。

共通 interface（概念）

class MacroDataProvider(Protocol):
    name: str
    # 与えられた series を、開始/終了範囲で取得し observation 列 + provenance を返す
    def fetch(
        series: SeriesDefinition, start: date, end: date
    ) -> Sequence[Observation]: ...
    # provenance = source_url, fetched_at_utc, frequency（freshness 判定に使う）
Provider モジュール取得方式 / 固有事情（module 内に隔離）担当ドメイン
FredProvider無認証 CSV（fredgraph）。series ID マッピングのみ米マクロ・金利・FX・原油 / 金・VIX・クレジット・BTC ＋ JP ミラー
JQuantsProvider認証トークン・rate limit。既存 screening 認証を共用JP 市場内部（業種指数・海外フロー・信用残・空売り）
EStatProviderappId・statsDataId・clunky JSON のパースJP 公式マクロ（失業率・CPI・鉱工業生産・小売）
BojProviderBOJ 時系列 CSV のコード体系政策・短観・money stock・JGB
CoinGeckoProvider無料 APIcrypto 詳細
ManualProviderclean API 無し。手動入力 / scrape を provenance 付きで取り込む倒産件数（東商 / 帝国 DB）・PMI

設計の要点

service / cache / registry は provider に依存しない。ソースの違い（認証有無・パース・rate limit・手動 fallback）は各 provider module に閉じる。これで「それぞれの実装を整理した状態」になり、Tier の拡張も provider 追加で局所化される。既存 stats/ の providers.py ＋ SeriesDefinition（provider / provider_series_id）が、この設計のそのままの種。

5. データソース → 優先度 → 担当 Provider

一般金融知識から広く候補を出し（10 ドメイン）、lever × 頻度 × JP 固有性 × 非冗長で序列化し、各 series に担当 provider を割り当てます。

候補（10 ドメイン・breadth）

  • A 金融政策・金利: 政策金利(BOJ/Fed/ECB)・JGB 2y/10y/30y・米 2y/10y・2s10s・実質金利/BEI・中銀会合カレンダー
  • B 物価: コア CPI(JP/US)・PCE・PPI・輸入物価・期待インフレ
  • C 景気・実体: GDP・PMI(JP/US/中)・鉱工業生産・短観・機械受注・小売・失業率・新規失業保険・倒産件数・住宅着工
  • D 市場内部・センチメント: 主要 INDEX(日経/TOPIX/S&P/NASDAQ/Russell2000/MSCI/中国/欧州)・TOPIX 33 業種指数・バリュー vs グロース style・VIX/日経 VI・breadth・信用残/信用倍率・空売り比率
  • E 為替: USD/JPY・EUR/JPY・DXY・実効レート
  • F 商品: 原油(WTI/Brent)・天然ガス/LNG・銅・金・農産物
  • G crypto: BTC・ETH・crypto 時価総額・funding rate
  • H フロー・需給: 海外投資家売買動向・信託/年金フロー・自社株買い・ファンドフロー
  • I 地政学・イベント: 選挙/政策/関税/紛争カレンダー・決算/指標発表カレンダー

取得の見通し

Fred ＋ JQuants（両方すでに配線済）＋ EStat / Boj（無料 API・新規 provider）で Tier 1–2 の約 80% が自動取得可能。ManualProvider 行きの 倒産件数・PMI だけが難所（Tier 2–3 なので後回し可）。実装時に FRED 系列 ID と J-Quants 各 endpoint の plan 可用性を検証する。

6. screening 接続（screen は macro-blind のまま）

マクロ読みが銘柄選択に効く形を第一原理から決めます。注入強度は 3 段階で、機械ふるい run には接続しないのが最適です。

案注入点評価
A 注意 / posture overlayselect（sector 優先）・policy（risk）・research（narrative）のみ。機械ふるいは触らない採用
B regime 条件付き screenregime で lane 重み / 閾値を可変却下
C universe 硬 gatemacro で sector を universe から除外却下

B / C を却下する第一原理

regime 条件付き閾値は ①パラメータ増＝§9 が禁じる data-snooping、②screen 出力が macro 判断に依存すると lane の大 N backtest が壊れる（lane alpha を純粋計測できない）、③regime は n≈1 の検証不能判断を validated な fact-engine に注入＝汚染、④value 戦略は「macro に嫌われた割安」を買って勝つので sector 減点はコア thesis と逆行。C はさらに fact 層を不完全にする。よって 構造的事実は screen、タイミング / posture 判断は overlay が境界線。

7. 既存を当て込む ＋ 進め方

理想構成が決まって初めて、現コードを当て込みます。

① データ（Provider 層）stats/（独立・providers.py・SeriesDefinition・coverage・FRED/Fed/ECB）約 70%。provider 追加（EStat/Boj/CoinGecko/Manual）＋ Tier-1 series 登録

進め方

この target が固まれば、km:plan で #257 を「L2 機械化 → macro capability / 独立サブシステム」へ作り直して Issue 化。実装順は ① データ取得層（Provider 設計 ＋ Tier-1 series）→ ② 分析成果 schema（lever 必須）→ ③ ナレッジ（軽量・都度）を薄く立ち上げ、各段で実運用テスト。stats/ の Provider 整理が最初の足場。

この版で簡略化したこと

前版にあった「第 3 のループ」「Frame→…→Retro の loop 図」「reuse ratchet / calibration log / 3 柱の成長判定機構」を削除。改善は都度行う前提に変更。残した誠実性の原則は 1 つだけ——macro は判断であって測られた driver ではない（edge 数値・統計的有意・自動売買 score を出さない）。重さはデータ取得層の Provider 設計に寄せた。
