1. 結論サマリ

サブシステム境界（macro / screening / position ＋ shared ＋ 横断 validation）は確定済み。本書はその中のモジュール・概念の命名を、ドメイン（個人バリュー株スイングトレード）の意味から洗い直す。狙いは「名前を見ればドメインでの役割が分かる」状態 ＝ AI がサブシステムを指定されてノイズなく即作業できること。

4 専門家が収束した結論

  • 確定した改名: ledger を screening/forward（計測）＋ position/decisions（決定記録）に分割／research→thesis／stats→series／price→bars／common→foundation／trade→position／validate→validation（単一 top-level に集約）／policy_config→policy。
  • 却下した造語: sieve（screening 自体がふるい＝同義反復）・triage（CLI select と desync）・conformance（造語・硬い）・各 context への検証 co-locate。
  • 奥まで通す: lane→playbook／payload/packet→具体型名／stats.domain field→category。
  • 論点（要判断）: macro の context/analysis 二分（§6）と、forward 計測層を forward と呼ぶか telemetry を残すか。

2. 命名以前に判明した 4 つの構造事実

DDD レビューが、命名の叩き台を実コード・実 records と突き合わせ、「命名問題」の半分が実は構造問題だと明らかにした。名前は構造を映すので、まず構造を正す。

#構造事実含意
Aledger/ は 1 パッケージに 2 つの bounded context が同居（position 系: sync/gates/benchmark ＝実取引／ screening 自己計測系: replay/cohort/ablation ＝取引でない）「名前の悪い 1 概念」でなく screening↔position を跨ぐ god-module。分割が本丸
Bmacro_analysis の構造化出力（trade_levers/risk_posture）は死蔵コード。消費者は自分と validator のみ。screening/selection が読むのは MacroContext だけ（records も裏付け: context 5 件が実駆動 vs analysis 1 件が本日作成・未配線）「macro を判断層に効かせる」配線が未完。命名と同時に解決すべき
Csector-tilt が 2 schema で二重定義（context: key/stance/strength ／ analysis: lever/target/direction）1 ドメイン概念・2 語彙＝教科書的ユビキタス言語違反が records 実体にある
Dvalidator は records（公開言語）軸で編成（01→04→05→06→_ledger）。コードの context 境界ではなく records パイプラインそのもの検証は context 間契約＝Published Language。各 context に散らさず単一 gate が正しい

3. 確立した命名原則

4 専門家が異なる角度から同じ原則に至った。これが個々の語を裁く基準になる。

  1. grounded ＞ plain ＞ clever-invented（AI 可読性）: 平易さ一辺倒でない。判定は「repo に既にある語か」。series/bars/decisions/thesis は型・records に既出だから採る。backtest/stats（誤解・漠然）は捨てる。sieve/conformance（造語）は却下。
  2. 投資家が話す語・1 概念 1 語（DDD）: ユビキタス言語は「ドメインエキスパートと開発者が同じ語を使う」こと。投資家は screen/candidate/forward/decision/stance/thesis/regime を話す。比喩語（sieve/triage/lane/lens/payload）は synonym を増やし翻訳コストを生む。
  3. 誤解語を捨てる（金融ドメイン）: backtest は historical simulation ＋ track-record を含意するが実体は forward-only の signal-efficacy 分析。quotes は bid/ask の意味で日次足には誤用（→bars）。ledger は会計元帳の含意（→decisions）。
  4. 縦の整合（package ＋ CLI ＋ records ＋ kind を丸ごと揃えるか、やらないか）（AI 可読性）: package だけ改名すると「stats→series だが CLI は baibai-loop-stats」という新たな一概念二語を生む。半 rename は無改名より悪い。

5. 新フォルダ構成（サブシステム別・命名根拠つき）

前回の横並びツリーは読みづらかったので、サブシステムごとに分け、各フォルダに「← 旧名 ／ 役割」を併記する。

5.1 macro — 環境を読む

macro/
├─ （§6 の判断で確定）        ← macro_context / macro_analysis
├─ series/                    ← stats        経済指標の時系列
│   ├─ providers/                            ソース別取得（FRED/eStat/BOJ…）
│   └─ definitions.py（category field ← domain）
└─（検証は横断 validation/ へ）

stats→series はコード（SeriesDefinition）と完全一致する grounded な改名。CLI も baibai-loop-series へ縦に揃える。

5.2 screening — 機械でふるう

screening/
├─ rules / metrics / universe / regime …    選別ロジック（fact-engine、据え置き）
├─ selection/                ← 維持          候補→推奨の ranking（triage 却下）
├─ forward/                  ← ledger 計測   forward returns の signal-efficacy 分析
│   （replay / cohort / ablation / forward_return）
└─（playbook ← lane、signal/score ← lens、具体型 ← packet/payload）

forward/ は backtest（誤解語）でも telemetry（非金融語）でもなく、forward-only という honesty 属性を名前で表す。CLI 計測サブコマンドはここへ。

5.3 position — 建玉の一生

position/
├─ thesis/                   ← validate/research   投資仮説（なぜ買うか）
├─ execution.py              ← trades              約定記録
├─ tracking.py               ← tracking            保有の forward 追跡
├─ decisions/                ← ledger register     決定イベント（保全対象）
├─ review.py                 ← review_gates        執行品質レビュー
├─ benchmark.py              ← 維持                対 INDEX 実績
└─ policy.py                 ← policy_config       portfolio policy（shared から移設）

ledger god-module を解体し、決定記録（decisions）と計測（screening/forward）を別 context へ。position は records/06-trades と CLI を縦に揃えて改名する。

5.4 shared ＋ 横断 validation

shared/
├─ foundation/               ← common（coerce/yaml_io/date_utils/_env/filesystem/jst）
└─ bars/                     ← price（JQuantsDailyBar 型 + price-walk）

validation/                  ← validate（単一 top-level・各 context に散らさない）
├─ cli.py                                    records 公開言語の検証 dispatcher
├─ findings.py               ← errors        ValidationFinding
└─（macro / candidates / thesis / trade / decisions の record 別 validator）

検証対象は「context 間契約 ＝ records schema」という単一の共有関心なので、validation/ 1 つに集約する（per-context conformance/ は CI gate を分裂させるノイズ）。

6. 最重要論点 — macro の context/analysis をどうするか

ここだけ DDD と AI 可読性が正面衝突した。両者とも「macro_analysis の lever が死蔵・sector-tilt が二重定義」という同じ事実を見て、逆の結論を出している。

案主張根拠リスク
A. 統合（DDD 既定）macro_context を唯一の published 成果物に。analysis の推論を rationale として畳み込み、死蔵 trade_levers と 02-macro-analysis を削除analysis は死蔵・二重定義・projection 未機械化。「計測経路のない機能を足さない／古い実装を捨てる」哲学に整合#257 で作った lever 駆動の野心を捨てる
B. 分離維持（AI 可読性）premise（前提）＋ judgment（判断）に分け、4 重の区別を保つ「screen は macro-blind」不変条件をコードが 4 重に担保。reading 統合で潰すと AI が judgment を premise に置き正しさを壊す死蔵・二重定義を温存（配線しない限り）
C. producer→consumer 2 層（私の統合案・推奨）judgment（研究イベント・lever 付き・複数）→ stance（published な読み・screening が消費・単数）の生産者→契約関係。sector-tilt 語彙は stance に一本化し、judgment を配線で生かすA の「死蔵・二重解消」と B の「分離・不変条件保護」を両立。#257 の lever 価値を活かしつつ macro-blind を守るjudgment→stance の projection 運用を回す手間

あなたに確認したいこと（DDD も「投資家本人の確認で確定」と明記）

macro を実際にどう運用しますか。(i) 複数の研究（テーマ別 judgment）を書き、それを 1 つの現在の読み（stance）に集約していくなら案 C（私の推奨）。(ii) その都度 1 つの環境読みを書くだけなら案 A（統合・シンプル）。あなたの「価値優先・死蔵を残さない」方針では、A も C も死蔵を解消します（A は削除で、C は配線で）。#257 の「lever でトレード判断を動かす」野心を残すなら C です。

7. 4 専門家レビューの統合

叩き台 v1 を 4 観点で壊しにいかせ、各々が独立に検証した。

専門家最も効いた指摘
DDD命名問題の半分は構造問題（§2 の 4 事実）。ledger 分割・macro 死蔵解消・validation 単一化が命名以前の本丸。投資家語・1 概念 1 語を死守せよ
金融ドメインdocs の「forward-only backtest」は語義矛盾（コード docstring は "not a backtest"）。backtest 回避は正、ただし telemetry も非金融語で forward が native。quotes→bars、ledger→会計誤含意
Python 命名構造判断は正しいが語の格が高すぎる。conformance/sieve/telemetry/triage は平易語へ引き戻せ。本丸は ledger 3 分割で churn は小さい（mock patch 文字列 6 箇所のみ）
AI 可読性(adversary)reading 統合が最危険（macro-blind 不変条件を壊す）。「半 rename」が一語二名を生む＝package＋CLI＋records＋kind を縦に揃えよ。原則「grounded ＞ plain ＞ clever」

4 者は sieve 却下・position・thesis・bars・validation 単一化・ledger 分割で一致。割れたのは macro（§6）と forward 計測層の語（forward 3 票 vs telemetry 残置 1 票 → forward 採用）のみ。

8. 残る確認事項

  • macro の運用（§6）: 案 A（統合・削除）か案 C（judgment→stance 2 層・配線）か。あなたの運用意図で決まる。
  • forward 計測層の語: screening/forward で確定してよいか（telemetry は docs に 31 件あるが「forward 計測」へ寄せる）。
  • 縦の改名範囲: stats→series・trade→position は CLI（baibai-loop-stats/-ledger）と records dir（01/06/_ledger）と kind: discriminator まで縦に揃える。この一括改名を最終 PR に含めてよいか。
  • foundation か core か: junk-drawer 抑止はどちらでも効く（微差）。
