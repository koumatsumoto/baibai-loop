1. エグゼクティブサマリ — 最終 PR が達成すること

3 つの issue を 1 本の最終 PR で統合してクローズする。狙いは「お買い得銘柄を拾いトレード成績を最大化する」システムを、サブシステム単位で理解・改善できる構造へ移すこと。

issue状態最終 PR での扱い
#257 macro capability 化実装済み・close 済み（#260/#261/#262）サブシステム分割の macro ピースとして組み込み、判断層への配線で完遂
#252 運用/改善 2 ループ分離docs は実質完了、残骸ありoverview.html 残骸 3 行 ＋ trade-review 文書化 ＋ records 判断記録
#258 src サブシステム再編未実装本 PR の本体 — package-by-subsystem ＋ 循環解消 ＋ CLI 分割 ＋ docs 軸一致

判断基準（ユーザ確定）

長期ビジネス価値 × 10 年保守性を最優先。挙動不変・後方互換・監査・厳密 no-regression parity は制約にしない（価値が上がるならリスクを取り挙動を変える。バグも許容）。唯一の例外＝実取引記録（ledger の decision register / trade の決済記録）の正確性は法務・税務で必須なので保全する。

この基準の下で、3 観点の対立レビューが「churn の割に価値の薄い部分（docs 全面物理移動の一部・7 項目 README 憲章の再記述・consumer のいない front-matter タグ）」と「価値が高く取りこぼせない部分（循環解消・shared 抽出・macro 配線・ledger 分割）」を切り分けた。最終設計はその切り分けを反映している。

2. ASIS — 3 サブシステムの非対称性という中心構造

3 つの独立した現状分析（src 依存 / docs 構成 / 改善ループ）が、いずれも同じ「macro・screening・trade の非対称性」へ収束した。これが再設計の背骨になる。

観点screeningmacrotrade
コード巨大・自立 12,186 行（本体）＋ 計測 7 本#257 で独立完成（stats ＋ analysis）ledger に埋没・追跡系が散在
docs唯一の subsystem dir（7 docs）散在・入口ゼロ・runbook 索引外で到達不能散在・品質改善の landing なし・runbook 37 行 stub
品質改善大 N backtest（成熟・参照モデル）N≈1 都度ナレッジ（完成・意図的に非計測）review 機構のみ・専用 runbook 欠落＝最大 gap

レビューが正した重要な事実誤認

「trade は薄い（660 行）」は execution/tracking だけを数えた計測 artifact。validate（trade 764 ＋ ledger 129 ＋ research 約 1,587…）を co-locate すると trade ≈ 3,400 行で 2 番目に大きい。真の非対称は「trade が薄い」ではなく screening が単一サブシステムとして 14,000 行に一極支配していること。対称化の根拠はこちらに置く。

2.1 構造問題 — screening ↔ ledger の循環と責務混載

ledger/ が「screening の forward 計測」と「trade の追跡」という 2 サブシステムの責務を混載し、screening との間にパッケージ循環がある。この循環が理解・変更コストの中核。

2.2 docs は 4 つの組織軸が混在

docs 49 ファイルは単一の構成原理を持たず、トピック軸（architecture / reference / governance / templates）・成果物軸（components）・活動軸（operations）・サブシステム軸（screening のみ）が併存する。サブシステム所属が dir 構造から復元できず、「macro を触る AI」は 5 つの doc と 2 つの records dir を stitch する必要がある（しかも macro-runbook は索引外で発見不能）。

3. 設計原則（10 年保守性の根拠）

  1. package-by-subsystem: 境界を技術レイヤーでなく業務ドメイン（macro/screening/trade）で引く。技術は変わるがドメインは安定 → 10 年スパンで境界が動かない。
  2. 対称な構造・固有の計器: 3 サブシステムは「入口・コード・records・品質改善・規律」を同じ骨格で持つ（AI が型で読める）。だが品質改善の計器は性質に応じて異なってよい（大 N backtest / N≈1 ナレッジ / 小 N review）。構造の対称化と計器の均質化を混同しない（honesty firewall）。
  3. 共有層は薄く、hub 化しない: 実際に複数サブシステムが使うものだけ。shared を新たな結合中心にしない。横断 dispatcher（validate）は shared に置かず独立 top-level に分離（レビューで是正）。
  4. schema をステージ間契約の一次構造に: 3 サブシステムは線形パイプラインで、横断変更（新シグナルが macro→screening→trade を貫く）の追跡に _schemas/ 契約が要る。パッケージは契約の帰結。
  5. 計測経路のない機能を足さない（CLAUDE.md）: 各品質改善の計器は具体的な「次の決定」を駆動できること。
  6. 整理・削除を優先、増設を最小化: 入口は薄い pointer（既存 doc への link）に留め、内容の再記述（rot 源）や consumer のいないタグを足さない。

4. TOBE: src 構成（ASIS / TOBE 比較）

技術レイヤー軸からサブシステム軸へ。ledger/ を seam で割り、循環を断ち、価格データを共有層へ抽出する。

レビューで是正した 2 点（「薄い shared」を設計自身が破っていた）

① validate/cli.py は全 validator を import する合成ルート（composition root）。shared に置くと shared→trade→shared の依存逆流になるため、独立 top-level に残す（errors/domain だけ shared へ降ろす）。② policy_config の実利用は trade 系のみ（screening 未使用）で shared 不適格 → trade/ へ。

4.2 循環解消（依存は単方向 DAG へ）

価格型・JST・atomic write を shared へ抽出すると、trade→screening のエッジが消える。resolve_price_on_or_before（計測 5 本と追跡が共用する純関数）も shared/price へ。残るのは screening→trade の片方向（保有照合）のみで、これは正当な単方向依存として許容する。

4.3 CLI 再編

baibai-loop-ledger（計測 ＋ 追跡を混載 dispatch する実 wart）を廃止。計測サブコマンド（lane-cohorts / screening-replay / selection-ablation …）→ baibai-loop-screening 配下、追跡 ＋ benchmark → baibai-loop-trade 新設、macro 統計 → baibai-loop-macro。baibai-loop-validate は横断のまま。互換 shim は作らない（CLAUDE.md が CLI 再編を許容、git history が安全網）。

5.2 入口は薄く・重複は削除（reorg ≠ dedup を分ける）

  • 薄い pointer 入口: 各 subsystems/<name>/README.md は「役割 1 行 ＋ コード/records/schema/CLI/品質改善/規律への link 列」。7 項目の内容再記述はしない（コード移動のたび 3 憲章を手更新する負債を避ける）。
  • 重複は dedup（その場で削除、git mv 不要）: candidates 契約 3 重 / sizing 3 箇所 / CLI 3 綴り（uv run に統一）/ anti-patterns.md 同名衝突。
  • rot 修正: configuration.md の削除済み実装言及、jquants-rate-limits の change-log 体を完成形へ。
  • subsystem: front-matter タグは見送り: それを読む機械（validator/CI）が無い限り consumer ゼロの YAGNI。入れるなら読む側を同 PR で作る時だけ。

移動時に壊れる隠れ結合（migration レビュー発見）

validate/cli.py に POLICY_PATH = Path("docs/portfolio-policy.md") がハードコードされ、baibai-loop-validate がこの doc を artefact として検証する。docs 移動を「純 git mv」と扱うと validate が落ちる。portfolio-policy の移動は POLICY_PATH 更新と同一 commit で行う。dated reports の旧 CLI 名は完成形なので書き換えない。

6. サブシステム別の品質改善 ＋ 2 ループ ＋ schema 契約

ユーザ要求の核心「各サブシステムごとに品質改善が行える」を、3 サブシステムの性質の違いに即して設計する。各サブシステムが固有の計器で品質を上げ、共通の改善ループ（GitHub Issue → 改訂 PR）へ証拠を流す。これは #252 の Q1/Q2/Q3 直交と一致する。

サブシステム運用での役割品質改善の計器Nlanding doc
macro環境読み供給（sector / risk / theme lever）都度ナレッジ蓄積（registry/runbook 追記）N≈1subsystems/macro/runbook.md ③
screening候補生成（機械 fact-engine）大 N forward backtest（lane-cohorts / replay / ablation）大subsystems/screening/backtest.md
trade執行判断・追跡小 N execution review（review_gates → counterfactual → veto）小subsystems/trade/review.md ★

trade/review.md は「新儀式」ではなく既存機構の集約

最大の gap（trade に品質改善の landing が無い）を埋めるが、発明はしない。既存の review_gates（+15/+30 営業日の due 算出）＋ backtest Axis D（judgment-gate counterfactual）＋ Axis F（opportunity-cost）を 1 枚に集約し、Q2 veto を改善バックログへ流す導線を文書化するだけ。これで trade が screening の backtest-runbook と対称の「品質改善 landing」を持つ。

6.1 運用ループと改善ループ（#252）

運用ループはサブシステムを横断するデータフロー、改善ループは各サブシステムの固有計器が共通バックログへ合流する構造。「trades＝screening 検証の ground truth」という旧文言は廃し、trade は Q2 veto/規律として効かせる（screening 効果の再測定にはしない）。

6.2 schema をステージ間契約の一次構造に（横断変更の追跡）

3 サブシステムは独立 bounded context でなく線形パイプラインで、ステージ間が _schemas/ で結合する。新シグナルが 3 パッケージを貫く「横の変更」を追えるよう、各 schema に producer/consumer マップを付ける。schema こそ stage を書き換えても生き残る安定インターフェース。

7. AI 即理解メカニズム

「macro を改善して」と指示 → docs/subsystems/macro/README.md 1 枚から設計・コード・records・schema・品質改善・規律へ最短到達。実現手段は足し算を最小化する形に削いだ:

  • subsystem 入口を 3 つ対称に配置（薄い pointer。再記述せず link で繋ぐ → rot しない）。
  • README portal と AGENTS.md に「サブシステム名 → 入口」の索引を 1 つ追加（現状は topic 軸のみで subsystem 導線なし）。
  • .claude/skills（bargain-selection / ir-research）↔ subsystems docs を相互リンク（現状は未連結の shadow navigation）。
  • schema producer/consumer マップ（§6.2）で横断読者の stitch コストを 1 段に。

なぜ「dir を作る」だけで散在が消えるのか（adversary の問いへの回答）

screening は subsystem dir を持つのに今も 5 dir に散在している。だから本設計は「物理 dir を作れば解決」とは主張しない。到達性は入口 pointer の linkが担い（code が物理的にどこにあっても link で繋がる）、物理 move が買うのは「縦変更の locality」と「循環除去」だけ。後者（循環除去・ledger 分割）は実価値、前者は macro/trade が大きいので限界利得が小さい — だから物理 move は decoupling が自然に生む再配置 ＋ ledger 分割を主とし、残りはオープン論点（§11）でユーザ判断を仰ぐ。
