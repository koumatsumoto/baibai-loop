1. これは何のシステムか（3 層モデルと 2 つのループ）

Baibai-Loop は、日本株の実データ（価格・財務・開示・規制）を機械的に収集・正規化し、固定ルールでスクリーニング・スコアリングし、その効果を forward 計測で検証し続けるデータ解析基盤です。AI と人間はこの基盤の出力を使って銘柄リサーチと売買判断を行います。目的はただ一つ、「お買い得銘柄を拾い、トレード成績を最大化する」ことです。

設計の中心にあるのは、事実・分析・判断を物理的に分けるという規律です。これを 3 層モデルとして表します。

層実体性質
L1 データ層 data/screening/market.sqlite（J-Quants 価格・財務 / EDINET metrics / JPX 規制） 全上場銘柄の再現可能な事実。coverage は fail-fast で検証する
L2 分析層 screen lanes・selection lenses・軸別スコア・forward telemetry（replay / lane cohorts / ablation）。機械ふるいの事実出力 = records/04-candidates/（candidates） 決定論的・閾値固定の機械処理。すべて forward 計測に接続する
L3 判断層 records/（research / trades、macro context）＋ reports/ 人間 + AI 下書きの解釈と判断。売買 record が L2 計測の ground truth を供給する

AI が触れる安定契約は 2 面だけ

AI / スクリプトが依存してよいインタフェースは、CLI の YAML 出力と SQLite schema の 2 つに固定されています。判断と帰責は人間（L3）に残し、AI は L1 / L2 の事実に grounded な下書きを作る、という役割分担です。

L2 と L3 の見分け方：決定論的な機械出力（fact）か、人間 + AI の解釈（judgment）か

層の所属は 物理的な置き場所ではなく 成果物の性質で決まります。判定基準はただ一つ、「人間の判断が入るか」です。同じ fact／judgment の分離が、銘柄の生成側と効果の計測側の両方に対称に効きます。

局面L2（決定論的 fact ＝人間判断なし）L3（人間 + AI の judgment）
銘柄の生成candidates（records/04-candidates/）— 閾値固定の機械ふるい出力research — 採否・thesis の解釈
効果の計測forward telemetry（screening-replay／lane-cohorts／selection-ablation）— 固定 horizon・固定 benchmark の機械計測reports/ ＋ retro — 数値を読んで「次に何を直すか」を決める解釈

candidates も telemetry も物理的には記録ディレクトリに置かれますが、中身は人間判断ゼロの決定論的出力なので L2 です（telemetry の数値は計測の一次資料として扱う）。L3 判断層に属するのは macro context・research・trades・reports のような解釈・判断です。なお後述の decision loop 表の「レイヤー」列（fact / analysis / execution …）は、この L1/L2/L3 とは別軸で各成果物の役割を示すものです。

2 つのループ（運用ループ ＋ 改善ループ）

Baibai-Loop は単一ループではありません。「検証済みの screening system を適用して売買判断に落とす運用ループ」と、「その system を検証・改善する改善ループ」を意図的に分けます。両者は接合点「検証済み system（rules / playbooks / config）」ただ 1 点で繋がり、カデンス・データ源・成果物がすべて別です。

あえて「やらない」こと（ただし screening の backtest は積極的にやる）

機械学習による予測スコアリング、自動発注、リアルタイム処理は対象外です。「単一の合成スコアや売買指示は出力しない」も中核原則で、スコアは軸別の座標であって判定ではありません。対象は基本 5〜40 営業日（2 か月以内）の long-only スイングで、短期 thesis が外れた場合に長期保有へ切り替えられる銘柄を優先します。

バックテストの線引き（よくある誤解）: これは「バックテストしない」基盤ではありません。screening（lane / lens / regime / 閾値）の効果は、過去週を look-ahead を排して replay する multi-axis backtest（§7、backtest-runbook の 7 axis）で積極的に検証し、その計測結果で lane や閾値を改訂します。避けるのは ① 未来データへの閾値 grid search・パラメータ最適化（data snooping 回避）② 累積リターン / Sharpe / MaxDD の track-record claim ③ trade 単位の累積リターン backtest ── の 3 つだけです。

2. L1 データ層：実データの収集パイプライン

すべての出発点は、全上場銘柄の事実を 1 つの local store data/screening/market.sqlite に集約することです（git には載せない再生成可能 store）。データソースは 3 つで、それぞれ専用のキャッシュ補完コマンドを持ちます。

ソース取得物取り込みコマンド
J-Quants（ClientV2） 上場一覧・普通株/市場区分/33 業種、日次 OHLCV、財務サマリー・会社予想 EPS、決算予定、営業日カレンダ bootstrap-cache --asof
EDINET（v2 / CSV） 有報・四半期・半期報告書の CSV から EV/EBITDA・net cash・FCF・capex 等の前処理済み metrics extract-edinet-metrics --asof --lookback-days
JPX（公開 CSV/Excel/HTML） 特別注意銘柄・整理銘柄・取引停止・上場廃止警告の規制 flag bootstrap-cache（JPX snapshot を含む）

J-Quants から使うメソッドは次の 5 点に固定され、EDINET の対象 docTypeCode は 120/130（有報・訂正）・140/150（四半期）・160/170（半期）に限定されます。

J-Quants method用途
get_eq_master上場一覧、普通株判定、市場区分、33 業種、信用銘柄区分
get_eq_bars_daily_range日次 OHLCV、20 営業日平均売買代金、60 営業日騰落率、750 営業日自己レンジ
get_fin_summary_range財務サマリー、会社予想 EPS、利益系概要値
get_eq_earnings_cal決算発表予定
get_mkt_calendar営業日カレンダ

収集 → 検証 → 実行の標準手順

screening の run は provider API に一切アクセスしません（cache_only で構築）。事前に SQLite を完全な状態にし、coverage 検証を通してから実行する、という fail-fast 設計です。

# EDINET metrics を更新してから screening を回す標準手順
uv run baibai-loop-screening bootstrap-cache       --asof 2026-06-12
uv run baibai-loop-screening extract-edinet-metrics --asof 2026-06-12 --lookback-days 540
uv run baibai-loop-screening verify-cache-coverage  --asof 2026-06-12
uv run baibai-loop-screening run                    --asof 2026-06-12

なぜ SQLite を「正本」にするのか

日次足テーブルは coverage の SSOT（single source of truth）で、欠損は「行の歯抜け」として直接観測します。range fetch 系（財務サマリー・カレンダ等）は「未取得」と「対象なし」を行の有無から区別できないため、source_coverage テーブルを別途ゲートに使います。JPX 規制は latest snapshot しか取れないので fetched_at_utc を記録し、asof と 7 営業日超ずれていれば fail-fast します。

3. L2 狭義スクリーニング：4 つの機械ふるい（OR 条件）

ここが「スクリーニングプロセスの中核ロジック」です。run は SQLite を入力に、全上場普通株（プライム/スタンダード/グロース、直近 20 営業日以上の bar 履歴あり）を母集団として、4 つの playbook-linked lane を評価します。

重要な設計判断：規模・流動性は「除外条件」ではない

時価総額・売買代金・上場期間・JPX 規制 flag は、スクリーニング段階では除外せず candidates に事実として記録するだけです。research 推奨への絞り込み（時価総額 100 億円以上、20 日平均売買代金 1 億円以上、上場 182 日以上、規制銘柄除外）は、後続の select（分析層 = selection.liquidity）で初めて適用されます。事実層と分析層を分けるための徹底です。

入力指標

各銘柄について、valuation・cash・cashflow・sales・価格変化の指標群を算出します。比較母集団は東証 33 業種の中央値（n<10 は市場全体に fallback）と、過去 3 年の自己レンジです。

  • valuation: PER（forward 優先・会社予想ベース、未公表時のみ trailing）、PBR、EV/EBITDA（EDINET 前処理済みかつ EV・EBITDA が共に正のときだけ採用）、P/S、PCFR
  • cashflow: OCF yield（CFO TTM / 時価総額）、FCF yield（EDINET 由来）
  • balance sheet: cash-to-market-cap、net-cash-to-market-cap（EDINET 由来）、price-to-equity、equity_ratio
  • price: price_change 1d / 5d / 20d / 60d、gap_from_52w_low、turnover_spike_5d（これらは select の fast-dislocation lens 用。機械ふるいの hard gate にはしない）

4 lane の OR 判定

下の 4 lane のうち最低 1 つを満たした銘柄が通過です。閾値の正本は records/_config/screening-rules/2026-06-19T000000+0900.yaml。複数 lane に hit した銘柄は research 優先度が上がり、evidence_hits[] に lane 名・playbook・hit 理由・判定に使った metrics が記録されます。

各 lane は実装上の slug（valuation-reversion など）で呼ばれ、それだけでは直感的に意味が掴めません。本書では各 lane を ① 金融における正式英語名 ② 本質を掴むための漢字要約名の 2 つをセットで併記します。下表が対応表です。

slug（実装名）① 正式英語名（金融一般名称）② 漢字要約名一言で言うと
valuation-reversion Valuation Mean-Reversion 株価評価の平均回帰（割安修正） 業種比・自己レンジ比で割安化した株価倍率が、平均水準へ戻るのを狙う
cash-rich-asset-discount Cash-Rich Asset Discount 現金潤沢・資産割安 潤沢な現金・純資産に対して時価総額が小さい銘柄を拾う（広義の net-cash／資産価値割安）

3.1 valuation-reversion ／ Valuation Mean-Reversion ／ 株価評価の平均回帰（割安修正）

「業種中央値比の下方乖離 + 過去自己レンジ下位」「60 営業日の急落 + valuation 下方乖離」「セクターローテーション起因の短期売り」を 1 lane に束ねます。PER は per_forward（会社予想）を primary、未取得時は per_trailing に degrade。EV/EBITDA は exact かつ正のときのみ使用。

主な閾値値
sector_median_gap_max（業種中央値比の上限）−0.2
self_range_percentile_max（自己レンジ下位）0.2
price_change_60d_max（60 日騰落率）−0.15
sigma_gap_max−1.0
除外 sector銀行・証券・保険・その他金融

金融業は規制資本・金利・与信サイクルの構造要因で mean-reversion 前提が成立しないため除外。一方、相対 valuation 比較には支障がないので電気・ガス業はこの lane だけ除外しません。

3.2 cash-rich-asset-discount ／ Cash-Rich Asset Discount ／ 現金潤沢・資産割安

BS の厚みで拾う lane。docs/operations/backtest-runbook.md §6 の 2026-05 lane-cohorts で 4 週 mean rel −2.14pt（baseline 比 +5.32pt）と全 lane 中最強のため、config の lane 優先順位でも先頭に置かれています。

条件閾値
cash_to_market_cap ≥0.4
price_to_equity ≤1.0
equity_ratio ≥0.3
営業赤字でない必須
operating_profit_yoy（deterioration gate）>−0.3
EDINET net_cash_to_market_cap（取得時）≥0.0

deterioration gate は「BS は rich でも営業エンジンが急減速した銘柄」を排除する後付けゲート。EDINET の net cash 条件は「J-Quants の CashEq が高くても有利子負債を引くと net debt」な銘柄を弾きます。除外 sector は金融に加え、CashEq が機械判定上膨張する卸売業（商社・問屋の運転資金）、land inventory が指標を歪める不動産業、規制設備産業の電気・ガス業。

3.3 cashflow-yield-discount ／ Cash-Flow Yield Discount ／ 現金創出力の割安（営業CF利回り割安）

PER では拾いにくい現金創出力を、期間正規化した CFO TTM から OCF yield として評価します。TTM が作れない銘柄はこの lane から除外。

条件閾値
ocf_yield ≥0.1
cfo_yoy ≥（必須）−0.2
operating_profit_yoy（deterioration gate）>−0.3
fcf_yield > 0（EDINET 取得時のみ enforce）必須

OCF が高くても営業利益 YoY が急減した銘柄、capex 先行で FCF マイナスの重設備会社（短期 mean-reversion で機械判定しにくい）を排除します。EDINET 不在で FCF が None の銘柄は data 不在として通過させます。除外 sector は金融＋電気・ガス。

3.4 sales-discount-growth ／ Sales-Multiple (P/S) Discount with Growth ／ 増収・売上割安

利益は薄いが売上成長が残る調整銘柄を拾います。

条件閾値
ps_sector_gap_max（P/S 業種中央値比）−0.4
sales_yoy ≥0.05
operating_margin_min（chronic loser floor）−0.05
営業赤字許容条件CFO 正 または 赤字縮小

「赤字縮小（−100B → −50B でも pass）」という escape hatch を operating margin の floor で defang し、慢性赤字会社を排除します。除外 sector は金融。

4. L2 リサーチ候補選定（select）：通過銘柄リストから着手候補へ

リサーチ候補選定（select）は、最新の通過銘柄リスト（candidates）とマクロ環境分析（macro context）を組み合わせ、個別銘柄リサーチに着手すべき候補を絞り込む 機械処理（triage 層）です。通過銘柄リストが「事実の成果物」なら、リサーチ候補選定は「推奨を作る機械処理」。最終採用判断は人間（L3）に残ります。

market regime lens（指数トレンドの中立化）

SQLite の日次足だけから benchmark proxy 1321（日経225 ETF）の 20/60 営業日リターンを計算し、相場局面を分類します。固定閾値で grid search はしません。

  • risk_on_rally（Risk-On Rally ／ 上昇相場・リスクオン局面、20 日リターン ≥ +3%）：このときだけ fast_dislocation の ranking boost を中立化します。anti-momentum な急落銘柄は指数モメンタムが強い局面で構造的に劣後するためです。
  • risk_off_selloff（Risk-Off Sell-Off ／ 下落相場・リスクオフ局面、≤ −3%）／ neutral_range（Neutral Range ／ 中立レンジ・横ばい局面）／ unknown（算出不能）：従来挙動と完全一致。

これはゲートではなく lensで、候補の除外はしません。benchmark_relative_20d が −0.03 以下の候補には risk tag benchmark_laggard_20d が付きます（「3pt 以上劣後は starter size 限定」という retro ルールの annotation 化）。

5. L3 リサーチ：investment memo の判断ロジック

research（records/05-research/**/*.md）は、candidates の事実と macro context を統合する分析層です。candidate_ref と macro_context_ref を必須入力とし、front matter に構造化した判断、本文に根拠を記述します。AI が下書きできるのは thesis / valuation snapshot / 仮説ドラフト等まで、最終採用判定・一次ソース URL 確認・失敗分類確定は人間のみです。

4 軸評価（単一総合点に畳まない）

候補数が少ない段階で統計的 weight 調整の根拠が無く、単一スコアは「なぜ選んだか」の学習信号を壊すため、合計点は算出しません。各軸に strong / weak / neutral の寄与度だけを付けます。

Catalyst有無 / freshness / 種別（経過営業日 + 一次ソース URL）
Positioning / liquidity空売り残高 / 信用 / 特別注意 / 貸借 / 出来高（絶対値 + 60 日推移）

原因仮説 + 反対仮説（構造リスク）を必須化

「なぜ一時的に割安か」の原因仮説に加え、全 packet で反対仮説（構造的な下落理由）を必ず書きます。構造的成長鈍化・ガバナンス懸念・技術的陳腐化・accounting 警戒・業界需要縮小・ESG/規制・大株主売り圧力・営業 CF 一過性・有利子負債/偶発債務など 10 類型から選びます。割安が「罠」でないことを能動的に反証する仕組みです。

以下では entry しない

Position sizing — paper proxy と real の二層

position は paper proxy layer（1 億円仮想資本）と real layer（実資金）の 2 観点で別 field に記録し、validator も別ルールで検証します。paper proxy は検証用の統一尺度、real layer は実際の破滅的集中の管理です。

thesis には必ず 2 つの観点を 1 行以上書きます。long-hold fallback（短期 thesis が外れて長期保有になっても耐えられる BS / CF / 配当・自己株買いの耐久性）と、AI long-term impact（AI による長期機会・脅威・今回判断での重み。AI 期待だけで採用や sizing を正当化しない）。

6. L3 トレード執行：注文・約定・集中度ゲート

research の採用結論は、まず 売買提案（GitHub Issue）として「どの銘柄を・いくらで・何株」の具体提案にまとめられ、人間が承認します（提案・承認の場は Issue、その決定の機械正規化は records/_ledger/）。trade（records/06-trades/**/*.md）はその承認済み判断に対する執行記録です。自動発注はせず、人間の発注を記録します。発注しなかった採用・見送り・保留は trade と呼びません。約定結果は改善ループへ Q2（執行品質）の信号として還流します。

7. フォワード計測ループ：ledger・multi-axis backtest・playbook feedback

loop を閉じるのが forward 計測です。records/_ledger/research-decisions/YYYY-MM.jsonl は append-only の decision register で、research decision（approved/deferred/rejected）と execution state を 1 行 1 event で正規化します。訂正は既存行を書き換えず event_kind: correction の追加 event で表します。decision_event_id が register 内の join key であり、trade record の order_intent_id と接続します。

バックテストの線引き：screening は backtest する／trade 累積は backtest しない

「バックテストをしない基盤」という言い回しは正確ではありません。screening 部分は、過去週を look-ahead を排して replay する multi-axis backtest で積極的に検証します（手順の正本は docs/operations/backtest-runbook.md の 7 axis）。一方、戦略の累積リターンを過去に fit する種類の backtest はしません。両者を分けるのが forward-only 規律の本体です。

対象backtest するか方法 / 理由
screening の lane / lens / regime / 閾値の効果する過去週を forward-only に replay（screening-replay / lane-cohorts / selection-ablation ほか 7 axis）。lane 削除・lane 順・regime lens の default ON 化はこの計測で決定した
閾値の grid search・パラメータ最適化しない未来データへの fit（data snooping）を避ける。regime 閾値 ±3% 等は事前固定し、観測後に最適化しない
戦略の累積リターン / Sharpe / MaxDDしない「過去 X 年で年率 Y%」の track-record claim を出さない（1 名運用でサンプル不足、overfit が必然）
短期トレード単位の累積 backtestしないtrade は forward-only に decision register と fill/exit を対比。判断 gate の効果は judgment-gate counterfactual（backtest axis D）で別途計測

その上で、4 種類の forward telemetry CLI が「何が forward return を生んだか」を計測します。いずれも勝敗の件数集計ではなく、outcome を playbook / evidence family / macro / sizing / execution に帰属させる feedback です。

CLI計測対象用途
ledger benchmark実保有 positions の絶対・相対リターンと attribution実トレードの事後検証
screening-replayrecommended queue（top N）の asof+1w/4w forward return（1321 比）profile 採否を 6〜8 週の実データで判断、直近 1〜2 週は hold-out
lane-cohorts週次 candidates の全銘柄を lane 別 cohort で集計playbook 改訂の一次資料（どの割安タイプが効いたか）
selection-ablationranking 構成要素・lane を 1 つずつ無効化した variant の Δfull機能の削減・維持判断の根拠

計測が設計判断を駆動する

config の lane 順や sector 分散の上限値は、コメントに計測根拠が紐づいています。例：lane 優先順位が cash-rich-asset-discount（現金潤沢・資産割安）先頭なのは 2026-05 lane-cohorts と 2026-06 selection-ablation の drop_lane Δfull が最大だから。diversity の max_recommended_per_sector を 1 → 2 に緩めたのは no_diversity variant が +1.9pt（4w）だったから。「計測経路を 1 行で説明できない機能は足さない」が貫かれています。

一言でまとめると

Baibai-Loop は 2 つのループです。運用ループは、事実（L1/L2）を決定論的に作り、段階的に厳しくなる規律（liquidity 絞り込み → lens → kill switch → regime ゲート → 集中度ゲート）で機械が裁量を縛りながら銘柄を 1 本ずつ通し、最後に「いくらで何株」の売買提案（GitHub Issue）を人間判断に上げます。改善ループは、screening が機能しているかを——母数が極小の個人売買結果ではなく——全候補の forward-only backtest（大 N）で検証し、改善項目を GitHub Issue で管理して rules / playbooks を改訂します。trades は screening 検証ではなく Q2（執行品質）の信号として還流します。「計測経路のない機能は足さない」が両ループを貫く設計思想です。

用語このリポジトリでの意味

lane-cohorts週次 candidates の全銘柄を evidence lane 別の cohort に分け forward return を集計。replay が推奨上位だけを見るのに対し母集団全体を見る、playbook 改訂の一次資料
selection-ablationranking 機能や lane を1 つずつ無効化した variant を replay し、各機能の寄与（Δfull）と推奨重複率を計測。閾値 sweep はしない

Δfull（delta full）ある機能を抜いた variant の forward return が、全機能 on（full）からどれだけ動いたか。負＝抜くと成績が下がる＝その機能に価値がある
cohort同じ条件でまとめた銘柄群（例: lane 別 cohort）
replay / ablation過去データで再現実行する ／ 機能を抜いて差分（寄与）を見る手法

retro月次・四半期の振り返り。hit 数・採用率・lane 別成否を見て閾値や playbook の改訂を議論する

backtest（multi-axis）screening の効果を過去週で計測する手順（backtest-runbook の 7 axis: replay / lane-cohorts / ablation / judgment-gate counterfactual / bootstrap CI / opportunity-cost / regime×lane）。trade 累積リターンの backtest とは別物
